# scrcpy-lan v5.0 升级文档

> 2026-10-08 · 上游 v4.1 → v5.0 · 分支 `v4.0-lan`
> 备份锚点：分支 `backup/pre-v5.0`、tag `backup-v4.1-lan`（= rebase 前的 a9d9ced7）

## 1. 背景：上游 v5.0 带来了什么

v5.0 于 2026-10-05 发布，是 v4.1（2026-07-12）之后**唯一**的新 tag（没有 v4.2 过渡版），
相对 v4.1 共 **64 个提交 / 85 个文件 / +3648 −645**。核心变化：

| 类别 | 内容 |
|---|---|
| 硬件解码（旗舰） | `--hwdec=auto\|disabled\|vaapi\|d3d11va\|videotoolbox`，默认 auto 且软解回退；Windows 走 D3D11VA、Linux VA-API、macOS VideoToolbox；官方称 CPU 占用降约 10 倍 |
| 解码架构重构 | 新增 `app/src/hwdec.c`、`egl.c`、`interop/`（d3d11va / vaapi / videotoolbox / software 四后端）；解码器独立线程；解码器创建从 demuxer 拆到 decoder；强制硬解失败即报错 |
| 视频缓冲 | packet 接收时间戳驱动缓冲、video regulator 背压、sink 返回三态 |
| 音频捕获 | 播放捕获改为匹配 **13 个 usage**，并修正 `voiceCommunicationCaptureAllowed` 必须在 `build()` 之前调用 |
| 依赖升级 | FFmpeg **9.0.2**（并从此要求 ≥ 6.0）、SDL **3.4.18**、dav1d **1.5.4**、platform-tools(adb) **37.0.1** |
| 其它 | Windows ARM64 发布；OTG 支持 `ANDROID_SERIAL`；UHID 部分键盘丢键、AltGr、`--time-limit` 竞争、camera 停止假告警、YV12 mipmap 修复；视频编解码新增 `vp8`/`vp9` |

对本项目的实际收益主要在**多设备同投场景的解码开销**（webui DeviceGrid 多路预览时 CPU 是瓶颈），
硬解在 Windows 默认生效，无需额外参数。

## 2. 代码升级（rebase）

`git rebase v5.0` 重放 64 个自研提交，**仅 1 处冲突**：

```
server/src/main/java/com/genymobile/scrcpy/audio/AudioPlaybackCapture.java
```

**冲突成因**：双方各自做了「全 usage 捕获」（撞车式重复劳动）。
- 上游 = 13 个 usage 的静态数组 + `@TargetApi(AndroidVersions.API_26_ANDROID_8_0)` + `build()` 顺序修复
- 本 fork（提交 `c9393b5f`）= 仅 MEDIA/GAME/UNKNOWN 三项 + 动态重配置（audioDup：会话中切换设备出声）

**解决**：以上游实现为基底，叠加本 fork 的动态能力 ——
`this.audioPolicy` 保存、`stop()` 注销策略、`setKeepPlayingOnDevice()` / `reconfigureIfNeeded()` /
`unregisterAudioPolicy()`、`read()` 顶部重配置检查。
合并结果 = 上游 13 usage 全捕获 + 本 fork 可动态开关设备出声，两边能力都不丢。

其余 9 个双向改动文件（`app/src/{cli,main,options,scrcpy,file_pusher}.c`、`app/meson.build`、
`release/build_windows.sh`、`server/build_without_gradle.sh`、`AudioPlaybackCapture.java`）
中除上述者外全部自动合并成功，`--no-adb` 局域网直连补丁未被 v5.0 的解码器重构踩到。

## 3. 版本串适配

server 的 `Options.parse()` 要求启动参数里的 client version 等于 `BuildConfig.VERSION_NAME`。
v5.0 上游已把 `server/build.gradle` 升到 `versionCode 50000 / versionName "5.0"`，因此：

- `lan/scrcpy-lan.sh`：启动参数第一位 `4.1` → `5.0`
- `lan/scrcpy-lan-daemon.sh`：同上（guard 启动 server 的那一行）
- `webui/internal/control/writer.go`：注释随之更新（`TYPE_AUDIO_DUP` 仍为 23）

## 4. 协议兼容

上游 v5.0 **未新增/改动控制消息类型**，最大仍为 `TYPE_SCAN_FILE = 22`
（`git show v5.0:server/.../control/ControlMessage.java` 实测），
本 fork 的 `TYPE_AUDIO_DUP = 23` 保持不撞号。服务端流格式未变（`device/Streamer.java` 上游未动），
webui 的流解析与原生代理无需改动。


### 5.5 打 release 包

上游 `release/package_client.sh` 只打官方客户端用法，本 fork 直接组自包含包（客户端 + 设备端 jar/脚本 + 说明）：

```powershell
$stage = "release\output\scrcpy-lan-v5.0-win64"
New-Item -ItemType Directory -Force $stage | Out-Null
Copy-Item dist\* $stage -Recurse -Force                     # 5.3 组装出的 dist（已剔除 FFmpeg 62 系）
New-Item -ItemType Directory -Force "$stage\lan" | Out-Null
Copy-Item lan\scrcpy-lan.sh,lan\scrcpy-lan-daemon.sh,lan\autostart.sh "$stage\lan\"
Copy-Item server\build\outputs\apk\release\server-release-unsigned.apk "$stage\scrcpy-lan-server.jar"
# + README-LAN.md（包内使用说明）
Compress-Archive -Path $stage -DestinationPath release\output\scrcpy-lan-v5.0-win64.zip -CompressionLevel Optimal
```

产物：`release/output/scrcpy-lan-v5.0-win64.zip`（7.7 MB，19 项，顶层目录 `scrcpy-lan-v5.0-win64/`）。
`release/work` 与 `release/output` 由 `release/.gitignore` 忽略，不入库。

## 7. 已知问题 / 备忘

| 问题 | 处置 |
|---|---|
| 本机 msys 装有 pacman 版 `mingw-w64-ucrt-x86_64-sdl3 3.4.16` | 构建前必须 `unset PKG_CONFIG_PATH` + `PKG_CONFIG_LIBDIR` 指向 deps install，否则会捡到系统 SDL3（v5.0 上游脚本已内置该逻辑） |
| Gradle 9.3.1 + AGP 9.1.0（上游 v5.0 升级） | 首次构建需联网下载（本机走直连 dl.google.com 可用，代理反而不通）；`~/.gradle` 无缓存时不要用 `--offline` |
| `app/deps/work` 交叉编译缓存 | 保留可加速重建；换 v5.0 后旧缓存（FFmpeg 62 系）已失效，脚本会按版本重建 |
| deps install 目录同时残留新旧 FFmpeg DLL | 组装 dist 时必须删掉 `avcodec-62.dll`/`avformat-62.dll`/`avutil-60.dll`/`swresample-6.dll`（v4.1 遗留），否则客户端目录混两套 FFmpeg（+11 MB，且 exe 实际只链接 63 系） |
| Gradle 直连 `repo.maven.apache.org` 会被 Connection reset | 用一次性 init script 把 buildscript/项目仓库指向阿里云镜像（`-I <init.gradle>`，脚本放在仓库外，不改机器配置）；`dl.google.com` 直连可用而本机代理反而不通 |
